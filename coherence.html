Keeping software coherent at agent speed

Agents write a growing share of the Fuz stack's code. Software is coherent when it still reads as one design: one way to do each thing, one name for each concept, documents that are still true, and checks that mean what they say. This page lists the ways agent-written code loses that, and what the stack does about each.

A failure can be held anywhere from a person's judgment to the shape of the system. Each rung down the ladder depends less on anyone remembering than the one before it, and usually takes more work to build. A rule moves along when its next form is simpler than the rule.

Claude Fable 5.2 wrote this page and its data file. Its claims were checked against the repos on 2026-11-17. The maintainer has not yet reviewed its rows.

What holds each failure

Design drifts to the model's average

Features that do not fit get built, and designs default to whatever the model has seen most often. Not yet reviewed by the maintainer.

Person: One owner per project

Status
Held
Does
One person sets each project's scope, design and non-goals, and agents write most of the code.
Fails
When a non-goal is not written down, and the agent fills the gap with its own defaults.
Cost
The project depends on one person, and a successor gets the code and its public docs but not the planning notes kept outside the repos.
Evidence
  • The mdz README, which says agents generated almost everything but the designs
  • mdz's written list of what it does not include
  • The Fuz contributing page, which asks for design discussion and limits pull requests to collaborators

Written: Conventions in loaded files

Status
Held
Does
The stack's conventions live in skill and project files that sessions load, each section leading with the rules that most often go wrong.
Fails
When a rule goes stale and misleads every session that loads it, and when rules pile up unpruned.
Evidence
  • The fuz-stack skill, the stack's written conventions
  • mdz's project file, one of the files a session in that repo loads

Tool: Lints for the mechanical rules

Status
Partial
Does
Lints and audits enforce the conventions that have a mechanical form: import paths, unique export names, denied Rust lints and the crate graph. Nothing checks naming, styling or scope.
Fails
When a green lint run is read as the conventions being followed.
Evidence
  • The fuz-stack skill on the flat namespace, which a build-time check enforces
  • The release audit, which holds the crate graph to its layering rules
  • The Rust lint rules, denied as errors in the gate

Shape: Fit is a judgment

Status
Out of reach
Why
Whether a feature belongs is a judgment about the whole design, and no structure makes that call.

A known mistake comes back

The same class of error repeats across sessions that share no memory. Not yet reviewed by the maintainer.

Written: The correction is written down

Status
Held
Does
When an agent gets something wrong, the correction goes into a file that later sessions load.
Fails
When a written warning is expected to prevent a mistake that only a check can prevent.
Evidence
  • The tsv fixture workflow's list of common mistakes, each with its symptom and fix
  • The grimoire skill, on a mistake becoming guidance

Tool: The gate

Status
Partial
Does
Types, lints, tests, format checks and drift checks on generated code run in each repo's gate, and in most repos CI runs them again on every push.
Fails
When green is read as correct. Agents push to the main branch, so CI reports after a commit has landed and the local run is the only check before it.
Evidence
  • gro's check task, the gate for the TypeScript repos
  • The Rust gate
  • tsv's raw-find scan audit, a named class of bug turned into a gated check

Shape: Impossible states do not compile

Status
Partial
Does
In Rust, closed sets are enums and input structs reject unknown fields. In TypeScript, schema objects reject unknown keys. The flags for what a server mounts have no default, so a new one fails compilation until every config states it.
Evidence
  • The Rust rules on type modeling
  • The twin reference on enforcement, where the flags for what a server mounts have no default
  • The schema rules, where an object rejects unknown keys

Green but wrong

Code passes its gates and is still incorrect, or a test passes whether or not the code is right. Not yet reviewed by the maintainer.

Person: Review after landing

Status
Partial
Does
The maintainer reviews commits after they land on the main branch, and versions, publishing and deploys stay with the maintainer.
Fails
When a defect sits on the main branch until that review reaches it.
Wanted
A view of the commits pushed across every repo, so the review has one place to happen.
Evidence
  • The grimoire skill, on review after a commit lands
  • fuz_forge's list of what is not built, which includes the cross-repo review surface

Session: Writer and reviewer loop

Status
Partial
Does
In long-running work, one writer changes the code and a read-only reviewer reports findings, and they alternate until a round finds nothing worth fixing.
Fails
When the reviewer's own severity grades are accepted, and a loop closes with wrong answers filed as minor.
Cost
The reviewer is another agent, so a round catches only what an agent can see.
Evidence
  • The grimoire skill, which describes the loop and its stopping rule

Tool: Oracles, mutants and control cases

Status
Partial
Does
Where a reference exists, a harness checks output against it. A few projects also break the code on purpose to show that a test catches it, and the careful harnesses first prove they can report a failure.
Fails
When both sides agree on the same bug, when the comparison never looks at the property that is wrong, or when a harness has no control case and reports success for reasons unrelated to the code.
Cost
A twin roughly doubles the implementation, and an instrument is software with its own bugs.
Wanted
Routine mutation and branch-coverage runs for tsv.
Evidence
  • The fuz installer's mutation gate, which breaks one behavior at a time and checks that a test catches it
  • fuz_schema's mutants, where a survivor needs a written reason
  • The tsv divergence detector's overmatching audit, which requires a negative case for each pattern
Listed

Status

Status
Partial

Status
Held

Tool: Figures computed from reports

Status
Partial
Does
The tsv benchmarks page computes every figure it publishes from committed reports that record their commit and machine, and a test fails when the prose stops matching the data. Elsewhere figures are written by hand.
Fails
When the benchmark behind a figure predates the current build: refreshing the reports is manual, and nothing checks their age.
Evidence
  • The tsv benchmarks, whose prose figures are computed from the reports
  • The tsv site's benchmarks notes, on the test that gates the prose

Status
Partial
Does
Agents condense raw notes into durable documents and delete finished items.
Fails
When documents only grow.

Written: Mark built from designed

Status
Partial
Does
Design docs in several projects mark what is built and what is only designed, and the written rules treat a wrong doc comment as worse than a missing one. No public rule asks for the status marks.
Evidence
  • A gro design doc that opens with its status
  • fuz_forge's list of what is not built
  • The rule that a wrong doc comment is worse than a missing one

Tool: Link and drift checks

Status
Partial
Does
The Rust workspaces fail on a broken doc link, tsv fails on any dead Markdown link or anchor in its repo, and each TypeScript gate fails when a generated file has drifted. Nothing checks links in the Markdown of the TypeScript repos.
Fails
When the links resolve and the sentences around them are no longer true.
Evidence
  • tsv's doc-link audit
  • gro's docs on checking generated files
  • The Rust lint rules, which deny broken doc links

Shape: Docs generated from source

Status
Partial
Does
API docs are generated from the source and the skill pages on this site from the skill files, so neither is written twice. Hand-written prose has no such source.
Evidence
  • The documentation system reference, on the pipeline from source to API pages
  • This site's skill docs generation

Two copies drift apart

Duplicated code diverges, a name is translated at a boundary, or a type says one thing while the validator checks another. Not yet reviewed by the maintainer.

Written: One name, one copy, no shims

Status
Held
Does
The written rules give one identifier to the same thing in TypeScript, Rust and SQL, allow no compatibility layers or re-exports, and move shared code into one place once its reuse is known.
Fails
When an outside consumer exists and the migration is no longer the maintainer's to finish.
Cost
The naming goes against TypeScript's usual convention, and a breaking change has to be carried through every consumer at once.
Evidence
  • The fuz-stack skill's shared rules
  • The twin reference on naming parity
  • The Rust rule to extract a shared leaf on the third copy

Tool: Drift checks and twin suites

Status
Partial
Does
Each TypeScript gate fails on a drifted generated file, and shared suites hold the wire-visible names and shapes of the TypeScript and Rust twins equal. The Rust legs of those suites run on demand, and nothing checks internal names.
Fails
When a path is tested on one backend only, and the twins agree on the happy path and drift at the edges.
Wanted
The Rust legs of the cross-backend suites in CI.
Evidence
  • The twin reference on enforcement
  • fuz_app's CI workflow, which runs the TypeScript legs and names the ones it skips
  • tsv's wire-type drift check

Shape: One schema, one library

Status
Partial
Does
Within TypeScript one schema gives each data shape its type, defaults and validation, and each shared concern has one library. The Rust twins and the wire types of tsv are written by hand beside what they mirror.
Fails
When a type is written by hand beside the schema it should come from.
Cost
A schema change cascades through everything derived from it.
Evidence
  • The schema rules
  • fuz_schema, the stack's one schema library
  • fuz_ui's changelog entry extracting mdz into its own library

A gate stops gating

A check skips, caps its run or falls back, and still shows green. Not yet reviewed by the maintainer.

Written: Read the exit code

Status
Held
Does
The written rules make the gate's exit code the pass condition, never its filtered output.
Fails
When a gate's output is piped through a filter that hides its exit code, and the commit follows anyway.
Evidence
  • The fuz-stack skill on the gate, which says to read the gate's exit code
  • The Rust gate, whose pass condition is the exit code

Tool: Suites fail on a skip

Status
Partial
Does
The suites of zap, fuz and pglet fail when a test program or a prerequisite is missing, and the pinned counts of tsv fail when a count moves. Elsewhere a skip may only warn.
Fails
When a skip stays green with a warning that nobody reads.
Cost
A loud failure interrupts work that a quiet fallback would have let continue.
Evidence
  • tsv's pinned gate counts, which fail when the set of graded files changes
  • pglet's CI workflow, which refuses to be green because a prerequisite was missing
  • The Rust testing rules, on suites that never pass by skipping

Shape: One gate definition, in tsv

Status
Partial
Does
tsv's CI runs the same check command a session runs, so the two lists cannot drift. Elsewhere CI lists its steps again. Nothing structural stops a commit whose local gate was red.
Evidence
  • tsv's CI workflow, which runs the same check command as a session does

Status
Held
Does

Tool: Size limits in CI

Status
Partial
Does
CI holds the WebAssembly builds of tsv, pglet and fuz_schema, and the native addon of tsv, under committed size limits. In gro and tsv, instruction counts are graded against a base on demand and held to no committed limit.
Fails
When the gated axis holds and the regression is on another: an instruction count is blind to code size.
Evidence
  • tsv's artifact validation, with its size bands
  • pglet's notes on size and startup
  • fuz_schema's CI workflow, which holds the WebAssembly build under a ceiling

Shape: Speed is a measurement

Status
Out of reach
Why

Fails
When a differently spelled command gets past a deny rule that matches by prefix.

Status
Partial
