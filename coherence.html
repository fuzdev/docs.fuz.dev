Keeping software coherent at agent speed

/coherence

Agents write a growing share of the Fuz stack's code. These are the practices the stack relies on to keep that code coherent, sorted by what does the work: a person's judgment at the top, the shape of the system at the bottom.

Judgment

A person decides.

Few hands hold the shape

Status
Practised
Practice
One person decides the scope, the design and what the system will not do, and agents do the implementation.
Catches
Features that do not fit, and designs that default to whatever the model has seen most often.
Costs
The project depends on one person, and a successor gets the code and its public docs but not the private planning notes.
Fails
When the non-goals are not written down, the agent fills the gap with its own defaults.
Evidence
  • The Fuz contributing page, on discussion before code
  • The mdz README, which says agents generated the code and a person the designs
  • mdz's written list of what it does not include

Conversation

Asked and checked again in each session.

Review in loops, with a stopping rule

Status
Practised
Practice
One writer changes the code and a read-only reviewer reports findings, and they alternate until a round finds nothing worth fixing.
Catches
Defects the writer cannot see in its own work.
Costs
Every round costs tokens and time, and the reviewer is another agent: the maintainer's own review comes after the commit has landed on the main branch.
Fails
When the reviewer's own severity grades are accepted, and a loop closes with wrong answers filed as minor.
Evidence
  • The grimoire skill, which describes the writer and reviewer loop

Treat claims as leads

Status
Practised
Practice
An agent checks a survey result, a review finding or its own summary against the code before anyone acts on it, and runs the reference tool or a small experiment before building on a guess.
Catches
Confident wrong statements, which read exactly like the right ones, and work built on a guess that a short run would have corrected.
Costs
Checking a claim repeats work that was already paid for once.
Fails
When someone accepts a claim that nothing uses a function from a search inside one package, without walking every consumer.
Evidence
  • The grimoire skill, under "Leads, not facts"
  • The tsv fixture workflow, which runs the reference tool first and stops for approval

Written rules

Files every session loads.

Write the taste down where the agent reads it

Status
Practised
Practice
Conventions live in files that each session loads, and when an agent gets something wrong the correction is added there.
Catches
Code that drifts toward the average of the model's training data, and the same error repeating across sessions that share no memory.
Costs
Rules pile up and need pruning, and a stale rule misleads every session that loads it.
Fails
When a written warning is expected to prevent a mistake that only a check can prevent.
Evidence
  • The fuz-stack skill, the stack's written conventions
  • The grimoire skill, on how a mistake becomes guidance
  • The tsv fixture workflow's list of common mistakes

Distill and delete

Status
Partial
Practice
Agents condense raw notes into durable documents and then remove the notes.
Catches
Stale statements that are trusted because they are written down.
Costs
Deciding what to delete takes judgment, and deleting the wrong thing loses a reason.
Fails
When documents only grow. Here finished items are deleted, but the planning notes keep growing and old material is more often archived than removed.
Evidence
  • The grimoire skill, on the lifecycle of notes

Mechanical checks

A tool gives the verdict.

Gates go green before anything lands

Status
Practised
Practice
Types, lints, tests, format checks and drift checks on generated code run on every change, and the native and WebAssembly projects also hold build size to a committed limit.
Catches
Whole classes of error that a reviewer would otherwise have to remember to look for.
Costs
Gates take machine time on every change and need upkeep of their own.
Fails
When green is read as correct. The serious defects in this stack's recent record passed the local gates and were caught by corpus comparisons, mutation checks, cold-read review and CI.
Evidence
  • gro, whose check task runs the gates for the TypeScript projects
  • The fuz-stack performance reference, on gating sizes and counters

Build against oracles and twins

Status
Practised
Practice
Where a reference exists, a harness checks output against it, with recorded results checked on every change and the live reference in heavier runs before a release.
Catches
Edge cases nobody thought to write a test for, because the reference and its corpus already contain them.
Costs
A twin roughly doubles the implementation, and a reference can be wrong.
Fails
When both sides agree on the same bug, when the comparison never looks at the property that is wrong, or when someone absorbs a difference without fixing, documenting or detecting it.
Evidence
  • tsv's syntax tree compatibility with Svelte's parser
  • The catalogue of tsv's deliberate differences from Prettier
  • The twin reference, on how the TypeScript and Rust twins are held together

Build instruments, and check them

Status
Partial
Practice
Where reading the code is the only check, agents build a tool to do the checking or break the code on purpose to show that a test catches it, and the careful harnesses first prove they can report a failure.
Catches
Defects that survive careful reading, and tests that pass whether or not the code is right.
Costs
An instrument is software with its own bugs and its own maintenance.
Fails
When the harness has no control case, and it reports success for reasons unrelated to the code.
Evidence
  • The fuz installer's mutation gate, which breaks one behaviour at a time and checks a test catches it
  • fuz_schema's mutants, which run the unmutated tests first
  • The tsv divergence detector, with its required negative cases

Race the candidates

Status
Partial
Practice
For hot paths, agents build competing versions and measure them on real workloads, so far mostly in the formatter's performance work.
Catches
Optimisations that were predicted to help and did not.
Costs
Prototypes cost tokens and machine time, and wall-clock numbers need a quiet machine.
Fails
When a micro-benchmark or a model of the cost stands in for the measured workload.
Evidence
  • fuz_schema's record of trades that were built, measured and not taken
  • fuz_schema's grading of a candidate against a baseline
  • The fuz-stack performance reference, on measuring before claiming

Claims as data

Status
Partial
Practice
Some figures are regenerated from recorded sources that carry their provenance, and documents are asked to mark what is built, what is designed and what is only proposed.
Catches
Figures that were true when written and are still quoted long after.
Costs
Every claim needs a source and a way to regenerate it.
Fails
When the benchmark behind a figure predates the current build and nobody reruns it.
Evidence
  • The tsv benchmarks, whose prose figures are computed from the reports
  • The syntax highlighter benchmark results
  • A gro design doc that marks what is built and what is only designed

Fail loud

Status
Partial
Practice
A check that skips, a capped run or a fallback path reports that it did so and does not exit as a success.
Catches
Gates that have stopped gating while still showing green.
Costs
A loud failure interrupts work that a quiet fallback would have let continue.
Fails
When a gate's output is piped through a filter that hides its exit code, which has twice put a commit with a failing gate on a main branch here.
Evidence
  • The fuz-stack skill, on reading the gate's exit code
  • The fuz-stack Rust reference, on suites that never pass by skipping
  • tsv's gate counts, which fail when the set of graded files changes
  • fuz_app's security doc, on turning a rate limiter off

Structure

The shape of the system rules it out.

One source of truth

Status
Practised
Practice
Shared code moves into a library on first use when a second consumer is known, every caller moves in the same migration, and no compatibility layer stays behind.
Catches
Two versions of the same thing drifting apart.
Costs
A breaking change has to be carried through every consumer at once.
Fails
When an outside consumer exists and the migration is no longer the maintainer's to finish.
Evidence
  • fuz_ui's changelog entry extracting mdz
  • The fuz-stack skill's rule against compatibility layers

One name per concept, schemas as the source of truth

Status
Practised
Practice
One identifier names the same thing in TypeScript, Rust and SQL, and each data shape has one schema that its type, defaults and validation come from.
Catches
Translation errors at a boundary, and a type that says one thing while the validator checks another.
Costs
The naming goes against TypeScript's usual convention, and a schema change cascades through everything derived from it.
Fails
When a name is translated at a boundary, or a type is written by hand beside the schema it should come from.
Evidence
  • The fuz-stack skill's shared rules
  • fuz_schema, the stack's one schema library
  • The twin reference, on keeping names the same across TypeScript and Rust

Keep the irreversible human, by mechanism

Status
Partial
Practice
Publishing, version changes, new dependencies and deploys stay with a person, and where possible the tooling refuses the action so the agent does not have to remember.
Catches
An unattended session doing something that cannot be undone.
Costs
Work waits on a person at exactly the outward-facing steps.
Fails
When the limit is only a written rule, as it still is for version changes and new packages, or a deny rule that a differently spelled command gets past.
Evidence
  • The repos tool's documentation of what it pushes and what it refuses

Make the loop fast

Status
Partial
Practice
Tools an agent calls in a loop are designed to answer in milliseconds.
Catches
Checks that get skipped because they are slow.
Costs
Speed work competes with features, and compiled languages have a slower inner loop.
Fails
When a fast targeted check stands in for the full gate before landing.
