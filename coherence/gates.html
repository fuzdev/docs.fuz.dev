Gates

A gate is a check that gives a verdict on a change. These are the kinds the stack runs, sorted by how soon each reports, as the oracles are.

The holds whose instances this table lists: Lints for the mechanical rules (Design drifts to the model's average); Drift checks and twin suites (Two copies drift apart); Oracles, mutants and control cases (Green but wrong); Suppressions that expire (A check is silenced instead of satisfied); Suites that fail on a skip (A gate stops gating); CI reruns the gate (A slow check gets skipped); Link and drift checks (A stale statement is trusted); Committed size limits (A predicted speedup that is not one); The gate (A known mistake comes back); Checks at the edges (Private content reaches a public repo)

Where a row speaks of a class of repos, the repos under it are the class's members, computed from this site's snapshot of each repo's files. A repo that reaches the same check another way, such as through a script its check script calls, is not listed unless the row names it. Read from the repos on 2026-11-19.

A row may carry probes: a string that a named file, check script or CI step of the repo must have, or must not have, for the row to still be true in the way a file can show. The tests of this site check the ones about a check script or a CI step against its snapshot of the repos, and the evidence task checks the ones about a file. A probe that passes says the file, script or step still has the text the row depends on. It does not say the check is sound. A probe reads only the text it names, so one that says a step is absent does not see the same thing reached through another script or switched on by an environment variable.

  • Every change In the gate a session runs before landing, and again in CI.
  • CI In CI on a push to the main branch or a pull request, and not in the local gate.
  • Release Before a release, and not on each change.
  • On demand When someone chooses to run it.

CI gaps

Where CI runs less than the local gate, or does not run:

  • The Rust gate of zzz and its cross-backend tests run only locally, and its CI is Node-only
  • zervo's CI builds and tests nothing, because its browser engine is too heavy to build on each push
  • blake3 has no CI, so its size limits and test vectors run only by hand and before a release
  • tsv-format has no CI, so its typecheck, build and tests run only locally
  • tsv's CI skips the two legs of its gate that read sibling checkouts, the wider Prettier round trip and corpus discovery
  • pglet's CI leaves out the WebAssembly and concurrency suites of its gate set
  • zap's CI has no build of gro's runtime, so the tests that evaluate config through it are skipped there, by an explicit allowance
