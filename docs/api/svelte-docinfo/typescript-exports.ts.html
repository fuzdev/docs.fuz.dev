typescript-exports.ts

Module-level export analysis: resolve every export of a TypeScript source file into a DeclarationAnalysis, including re-export classification.

Builds on the per-declaration extractors in typescript-extract-*.ts by adding the orchestration layer — alias chain walking, namespace classification, JSDoc routing for re-exports, default-slot handling.

  • ``typescript-extract-*.ts`` for the per-declaration extractors

(sourceFile: SourceFile, ctx: ExtractContext, options: ModuleSourceOptions): ModuleExportsAnalysis import {analyzeExports} from 'svelte-docinfo/typescript-exports.js';

Analyze all exports from a TypeScript source file.

Extracts the module-level comment via extractModuleComment (skipped for svelte2tsx virtual files — see the inline note), star exports via extractStarExports, and all exported declarations with complete metadata. Handles re-exports by:

  • Same-name re-exports: tracked in reExports for alsoExportedFrom building
  • Renamed re-exports: included as new declarations with aliasOf metadata
  • Import-then-export (import {foo as bar} from './x'; export {bar}): encoded as its export-from twin, since rename detection steps through import bindings (nextExportHop)
  • Star exports (export * from): tracked in starExports for namespace-level info
  • Direct external re-exports: tracked in externalReExports/externalStarExports (specifier as written; import-then-export and source-chained forms stay silent)

This is a mid-level function (above the individual extract* helpers, below analyze) suitable for building documentation, API explorers, or analysis tools. For standard SvelteKit library layouts, use createSourceOptions(process.cwd()).

extractModuleComment
#

typescript-exports.ts view source

internal

Used by `analyzeTypescriptModule` and `analyzeSvelteModule`'s script handling. Exposed via the `svelte-docinfo/typescript-exports.js` subpath so the Svelte analyzer can reuse it without circular imports, but **not part of the stable barrel export**. The module comment is the first `/**` comment with a line starting with `@module`; later ones are ignored. It parses through `parseModuleComment`, so its tags read as a declaration's do and `@module` lines (with any `@module custom-name` rename) are dropped. `toModuleDocFields` projects the result onto `ModuleJson`, and `warnModuleCommentTags` reports the tags it drops.

warnModuleCommentTags
#

typescript-exports.ts view source

internal

Split by source, not by file type: `analyzeExports` covers TS files only — it skips a svelte2tsx virtual, where hoisted instance-script comments would read as module comments — so `analyzeSvelteModule` owns all three Svelte sources (instance script, `<script module>`, HTML comment), reading each from the original file.

(moduleDoc: TsdocParsedComment | undefined, diagnosticFile: string, diagnostics: ({ symbolName: string; file: string; line?: number | undefined; column?: number | undefined; message: string; severity: "error" | "warning"; kind: "type_extraction_failed"; } | ... 22 more ... | { ...; })[]): void import {warnModuleCommentTags} from 'svelte-docinfo/typescript-exports.js';

Warn misplaced_tag for each tag a module comment carries that only describes a declaration: @param, @returns, @mutates, @throws, @default, @nodocs, and @cssprop (a component's). toModuleDocFields drops them, so in a module comment they do nothing. @nodocs applies to declarations and export statements; to omit a module, use exclude patterns.

Reads the parsed comment, so a tag counts when parseComment extracted it: a bare @returns or @throws with no text is dropped without a warning, as on an overload. Unknown tags drop silently, as on declarations.
