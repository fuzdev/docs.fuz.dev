typescript-extract-type-properties.ts

internal

Property extraction for TypeScript type aliases, and for the computed heritage of interfaces.

extractTypeAliasProperties walks the resolved type and emits members for named properties, index signatures, call signatures, and construct signatures. Handles object literals, intersections, mapped types (Partial, Pick, Readonly, etc.), type references, and function types. Called by extractTypeInfo in typescript-extract-type.ts for type aliases. Interfaces walk their own node.members there, and take what a computed extends entry contributes from extractComputedHeritageMembers, which projects it the way this module projects an alias.

see also

  • ``typescript-extract-shared.ts`` for shared helpers

  • ``typescript-extract-type.ts`` for the dispatcher

extractComputedHeritageMembers

typescript-extract-type-properties.ts view source

(node: InterfaceDeclaration, heritageTypes: readonly ExpressionWithTypeArguments[], declaration: DeclarationJsonBuild, ctx: ExtractContext): ContributedSignatures import {extractComputedHeritageMembers} from 'svelte-docinfo/typescript-extract-type-properties.js';

Emit the members an interface gets from its computed heritage.

An interface's members are its own, plus what each extends entry that isn't a named interface or class contributes (isNamedHeritageType). A named base has its own declaration, which extends names, so its members stay there. A computed type has none: `interface A extends z.infer<typeof S> {}, the author-side fix for alias_lost`, or interface A extends Omit<Base, 'b'> {}, would otherwise document no member reachable anywhere. Each computed entry contributes what the same type documents as a type alias's members (extractTypeAliasProperties): its properties through the same projection (emitPropertyMembers), filtered by the same external-origin and visibility rules (filterDocumentedProperties; the labels for what that drops come from applyHeritageExternalTypes, which walks the same entries), then its local string and number index signatures. So a computed type over a named interface (Partial<Base>, Pick<Base, 'a'>, Base & {c: C}) lists the base's properties it keeps, as the alias would, and a project type alias in extends, an object type with no declaration of its own, contributes too, even when it is documented itself.

Which entry a name comes from follows TypeScript's inheritance: a name the interface declares wins, then the first heritage entry, named or computed, that has the name. The declared names are read from every merged block (symbol.members), though only node's block is documented (its members by extractTypeInfo, its extends here): a name another block declares drops from the contribution and documents nowhere, which is right where it overrides the heritage's type, and the other block's members going undocumented is a limitation of the one-block reading, not of this rule. A name a named base supplies first stays that base's; one an external bag supplies first is dropped. An index signature likewise comes from the first entry with that key type, unless the interface declares one. Contributed members follow the own ones, entry by entry in heritage order, each type's properties in the checker's order, then their index signatures. They carry no sourceLine, like every member.

Call and construct signatures go by declaration the same way: the first entry whose type has a signature declaration claims it, so one a named base supplies first stays the base's even when a later computed entry reaches it too (extends Base, Base & {…}), and each declaration is contributed once. The caller emits them, since they join the own signatures as overloads of one member (extractTypeInfo).

(node: TypeAliasLike, nodeType: Type, declaration: DeclarationJsonBuild, ctx: ExtractContext): void import {extractTypeAliasProperties} from 'svelte-docinfo/typescript-extract-type-properties.js';

Extract properties from a type alias via the TypeScript checker API.

Handles object literals, intersections, mapped types (Partial, Pick, Readonly, etc.), type references, and function types. Extracts:

  • Named properties (with readonly/optional detection, TSDoc from declarations)
  • Index signatures (string/number)
  • Call signatures ((call))
  • Construct signatures ((construct))

A JSDoc typedef reads the same way: a @typedef {object} builds its properties from @property tags (each tag's description is the member's docComment, and a bracketed [x] or {T=} makes it optional), and a @callback is a function type, so it gets a (call) member whose parameters and return carry the callback's @param/@returns text.
