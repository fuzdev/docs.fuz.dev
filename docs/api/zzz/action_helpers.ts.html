ACTION_PAYLOAD_BUDGET
#

action_helpers.ts view source

8192 import {ACTION_PAYLOAD_BUDGET} from '@fuzdev/zzz/action_helpers.js';

The most JSON, in characters, the actions log keeps of one payload — an action's input, output, progress, request params, response result, notification params, or error data. A larger payload is replaced by an ActionPayloadOmitted marker, so the log's 512 entries stay small even when calls carry file contents (session_load, diskfile_update) or whole chat histories (completion_create).

bound_action_event_data

(data: { kind: "request_response" | "remote_notification" | "local_call"; phase: "send_request" | "receive_request" | "send_response" | "receive_response" | "send_error" | "receive_error" | "send" | "receive" | "execute"; ... 9 more ...; notification: { ...; } | null; }, budget?: number): { ...; } import {bound_action_event_data} from '@fuzdev/zzz/action_helpers.js';

Bounds what the actions log keeps of an action event's data: each payload over budget — input, output, progress, the request's params, the response's result (or its error's data), the notification's params, and the error's data — becomes an ActionPayloadOmitted marker, and an error message over budget characters is truncated (see truncate_action_error_message) and flagged with ACTION_ERROR_MESSAGE_TRUNCATED_KEY. The lifecycle fields (kind, phase, step, method, executor), the JSON-RPC envelopes, and the error's code are always kept, so the result still parses as ActionEventData. Returns data itself when nothing is over the budget.

QUIET_ACTION_METHODS
#

action_helpers.ts view source

ReadonlySet<string>

type ReadonlySet<string>

import {QUIET_ACTION_METHODS} from '@fuzdev/zzz/action_helpers.js';

Methods the app calls as flow control rather than on anyone's behalf, many times a second: terminal_ack under a flood of terminal output. Their calls are kept out of the actions log, whose bounded history they would turn over in seconds, and a failed send isn't reported by the dispatcher's log (create_quiet_action_log) — the caller handles its own failures, some of which are expected (an ack racing its terminal's close).
