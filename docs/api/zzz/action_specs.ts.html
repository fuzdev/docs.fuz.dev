ActionSpecUnion[]

type ActionSpecUnion[]

import {all_action_specs} from '@fuzdev/zzz/action_specs.js';

Canonical action spec list — fuz_app's protocol actions (heartbeat, cancel) plus zzz-owned specs. Single source of truth for codegen and runtime registries (Frontend.action_registry, Backend.action_registry).

Codegen helpers default-filter protocol actions out of typed surfaces (FrontendActionsApi, BackendActionHandlers, ActionMethod, etc.) since they're dispatcher-owned. Server WS registration pairs protocol specs with fuz_app-shipped handlers via protocol_actions; iteration over all_action_specs skips them via is_protocol_action_method to avoid double-registration. Adding a future protocol action requires no consumer edit — fuz_app's protocol_action_specs is the upstream canonical bundle.

{ contents: string | null; unloaded_reason: "too_large" | "not_utf8" | null; hash: string | null; size: number; ctime: number | null; mtime: number | null; } import {DiskfileReadOutput} from '@fuzdev/zzz/action_specs.js';

Output for diskfile_read. contents is null exactly when unloaded_reason says why, and hash is null with it: otherwise it's the BLAKE3 of the bytes read (bare lowercase hex) — what a save based on these contents sends back as diskfile_update's expected_hash. size is in bytes: the contents' length when they're loaded, the bytes read when they aren't UTF-8, and for a file too large, its size when opened — or the limit plus one byte, a lower bound, for one that grew past the limit during the read. ctime / mtime are a disknode's (whole milliseconds since the epoch, null when the backend couldn't say), taken before the read, so a write racing it leaves them older than the contents, never newer.

Input for diskfile_update. expected_hash makes the save a compare-and-swap: the hash of the diskfile_read the edit is based on, and the file is written only if it still holds those bytes — else conflict / disk_changed, nothing written. Omitted, the save writes whatever is on disk: forcing a write the client can't base on a read. Recreating a deleted file is diskfile_create, exclusive, not this.

The fields here are the actual session snapshot — files and the roots they cover, scoped dirs, provider status, projects, the caller's terminals, and the server instance. The frontend loads it at boot and again after every reconnect, reconciling its state to it (see Frontend.load_session).

TODO extract to diskfile_types.ts (or a session-specific module) once the Rust backend grows its own typed session response and we can move this schema to the shared boundary.

Every indexed file's metadata, grouped by filer dir (decode_snapshot_files).

The roots of the backend's permanent filers and the ones the open projects keep, each covered by files as deep as its filer indexes — a whole tree, or a registry root's top level alone. A known file under one of them that files lacks is no longer indexed: gone from disk, or in a repo under a registry root that isn't focused.

type Branded[]

type ProviderStatus[]

type ProjectInfoJson[]

The daemon's project rev when projects was read: every project change up to it is in them, and none after. A held project the snapshot doesn't list is closed only when the rev held of it is no newer. files are read after it, outside the lock: a change committed between can show in them, and on a socket its project_changed arrives before this reply.
