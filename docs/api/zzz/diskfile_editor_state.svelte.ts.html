DiskfileEditorState
#

diskfile_editor_state.svelte.ts view source

import {DiskfileEditorState} from '@fuzdev/zzz/diskfile_editor_state.svelte.js';

The editing state of one file, shared by every view of it — the /files editor, file-part editors, tabs — and kept while none is mounted, like a VS Code text model. Get it with Diskfiles.get_editor_state, which creates it on first use and keeps it until nothing holds the file and it has nothing to keep (can_drop), or the diskfile is removed; views never own it.

It holds the file's DiskfileHistory, and records every change of the file's content on disk into it (Diskfiles calls check_disk_changes whenever new content lands), whether or not an editor shows it — having an editing state keeps a file's content current (see Diskfiles.upsert):

  • The content loads on demand: the views call Diskfiles.ensure_content. Until it lands the editor is read-only, and its first arrival seeds the history's original state — it's not a change on disk.
  • The editor shows the selected history entry (current_content), or the disk content when none is selected. A clean editor follows the disk.
  • Editing keeps the file's one draft (draft, in Diskfiles.drafts — not in the history, so it outlives this state and the file's cell), updated in place and re-dated on each edit. The views list it with the history (content_history, as draft_entry). Editing from another entry (an older state picked from the history) starts a new draft and sets the old one aside as a discarded-edit entry, so its text stays restorable.
  • When the disk changes under a draft, or under a picked entry, the edit is kept and has_conflict is set: saving stops until the user chooses to overwrite (save_changes({overwrite: true})) or keep the disk version (discard_draft). Our own save's broadcast never counts — the disk then holds the edit, which settles it. The backend checks too: a save carries the hash of the disk content it's based on (last_seen_disk_hash), so a write the frontend hasn't heard of yet refuses it (disk_changed), and the file is read again to show that change as a conflict like any other.
  • During a conflict the views can show the disk content instead, read-only (showing_disk, shown_content), without touching the edit.

check_disk_changes

Records the diskfile's content in the history if it changed on disk since last seen. Diskfiles calls it whenever new content lands, so the history tracks the disk whether or not an editor shows the file; calling it again is a no-op — a re-read of the same text changes nothing.

The first content to land for a state made before the file loaded seeds the original state instead: it's the file as first seen, not a change on disk, so it never reads as a conflict.

A clean editor moves to the new disk content. An editor showing the user's content keeps it, and the change becomes a disk_conflict — unless it's that very content (e.g. our own save's broadcast, landing after an external edit's), which settles the editor, or the content of the save in flight (our own write, with typing continuing past it).

type (): void

returns void

save_changes

Save changes to the diskfile. History, selection, and the modified flag change only once the write succeeds; a failure leaves the edit unsaved and sets save_error — including a write that throws, so this never rejects. One save runs at a time: saving while a write is in flight queues a single follow-up save (repeat calls share it) that writes whatever the editor holds once the first settles — skipped if that write failed. If the editor or the disk moves on while the write is in flight — more typing, another history entry picked, an external edit landing after the save's own — the saved content is recorded in history without taking over the editor.

Refuses, writing nothing, while has_conflict — unless overwrite — so a change made on disk under the edit is never overwritten silently. A change on disk arrives as metadata and the content follows by a read, so a save waits for a read of the file in flight or queued (Diskfiles.pending_read, save_pending meanwhile) and then decides as above, on the content it brought. If the file's last read failed (content_error) — the disk may hold a change it never brought — the save reads it once more and decides on that; a second failure refuses, with save_error saying the file couldn't be checked. An overwrite writes without that retry. A file whose content isn't loaded is never saved: this sets save_error.

The backend checks as well, closing the window the frontend can't see — a write it hasn't been told of yet: the save carries the hash of the disk content it's based on (last_seen_disk_hash), and is refused, writing nothing, if the file no longer holds it. The file is then read again (save_pending meanwhile), so the change lands like any other — a conflict under the user's content, whose notice says why it wasn't saved. An overwrite is checked the same way, against the disk version the user was shown and chose to write over — taken when it's asked for, so a newer version whose read lands while the save waits for it is refused, not written over unseen, and the refusal says so in save_error (SAVE_ERROR_CHANGED_AGAIN). If the file's last read had failed (content_error) when it's asked for, there's no version the user can trust as shown, and the overwrite writes over whatever is there, even once a read lands meanwhile. A save of a file deleted on disk is an exclusive create, refused if anything is at the path — so a file something else recreated meanwhile is read, not replaced. An overwrite queued behind a save in flight takes its base when it runs, after that save: the base moves with what that save wrote, and so with any change recorded while it was in flight.
