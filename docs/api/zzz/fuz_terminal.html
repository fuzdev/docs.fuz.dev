fuz_terminal

20 modules

  • fuz_terminal/fuz_terminal_deps.ts

    What a terminal view takes from its environment — loading the emulator, frames, a timer, resize observation, measuring, and the selection and clipboard a copy reads and writes — as one interface with browser defaults, provided through Svelte context so a test can step frames and inject measurements without faking globals.

  • fuz_terminal/fuz_terminal_frame.ts

    The frame loop a terminal view draws through: at most one frame pending, requested when something may have changed and idle otherwise — never a perpetual requestAnimationFrame.

  • fuz_terminal/fuz_terminal_key_target.ts

    How a page tells that a key belongs to a terminal view: the attribute the view's root carries while it takes keys, and the check a page's global shortcuts make. Apart from the keyboard module, so a page that only checks for a terminal loads none of the key encoding.

  • fuz_terminal/fuz_terminal_keyboard.ts

    A browser KeyboardEvent as a GhosttyKeyInput: the physical key from code, the modifiers, the text the key produced, and the key's unshifted code point — plus which keys the terminal leaves to the browser and the OS. Pure functions over the event's own fields (FuzTerminalKeyboardEvent, so tests pass plain objects); nothing here touches the DOM or the module.

    The unshifted code point is the key's text when the event shows it — an unshifted key's own text, a shifted letter lowercased — and otherwise the character the key makes on a US layout (FUZ_TERMINAL_US_UNSHIFTED): the browser exposes no layout table every engine has. So on another layout a shifted digit or punctuation key reports its US character, which the Kitty keyboard protocol sends as the key's code.

  • fuz_terminal/fuz_terminal_layout.ts

    The DOM renderer's geometry — pure functions over plain frame data and measurements, no DOM: the terminal's size in cells from its box, the pieces a row's runs are drawn as, and where the cursor goes.

  • fuz_terminal/fuz_terminal_state.svelte.ts

    The state behind FuzTerminal: one view's emulator — its own module instance, terminal, and render-state reader — and the frame loop that reads it into the plain frame data the component draws.

  • fuz_terminal/fuz_terminal_style.ts

    Turning the render-state reader's styles and colors into CSS for the DOM renderer — pure functions over plain frame data, no DOM.

    Colors reach CSS through custom properties on the terminal's root element, never as colors read into JS from the theme:

    • --fuz_terminal_fg / --fuz_terminal_bg — the default text color and background in effect. The stylesheet sets them from the theme; the root's inline style overrides them once a program has set its own (OSC 10 and 11; to_fuz_terminal_theme_css).
    • --fuz_terminal_palette_0 … --fuz_terminal_palette_255 — every palette entry. The first 16 come from the theme in the stylesheet unless a program changed one (OSC 4); the rest are the frame's own colors, set inline.
    • --fuz_terminal_cursor — the cursor's color: the theme's, falling back to the text color in effect, unless a program set one (OSC 12), which the view sets on its own.

    A style's CSS (to_fuz_terminal_style_css) names only those properties and colors formatted here from numbers, so it depends on the style alone: a palette change restyles every run through the custom properties without re-rendering a row.

  • fuz_terminal/ghostty_callback_table.ts

    The function pointers a libghostty-vt instance's callbacks are passed as: slots added to its __indirect_function_table, each holding a trampoline that calls a JS function. A wasm table can grow but never shrink, so its callers add a slot once per callback they keep for the instance's life.

  • fuz_terminal/ghostty_effects.ts

    Effects: the callbacks through which a libghostty-vt terminal asks its host for what it can't do itself — reply to the program (write_pty), ring the bell, announce a new title or working directory, hold the screen still while the program redraws it (render_hold).

    GhosttyTerminal.set_effect registers and clears them; this module holds what they share. Each effect has one trampoline per module instance, a slot in its function table (GhosttyCallbackTable) added the first time any terminal registers that effect. The library passes every callback the terminal handle it fired for, and GhosttyEffectRouter dispatches on it to the terminal attached under that handle — so the table grows by at most one slot per effect however many terminals come and go. No userdata pointer is set.

    An effect left unregistered is ignored by the library: a query gets no answer, a bell rings nowhere. That's how output is replayed without answering stale queries — feed it with no write_pty registered. The other effects the library has (clipboard read and write, desktop notifications, the size, color-scheme, device-attributes, enquiry, and XTVERSION responders, semantic prompts, unknown sequences, and more) aren't bound, so they're never registered. The clipboard ones stay that way until there's a way to ask the person first.

  • fuz_terminal/ghostty_errors.ts

    The errors the libghostty-vt binding throws: a module that can't be used, a type manifest missing what the binding needs, a call that returned a failing GhosttyResult, a handle used after it was disposed, a terminal called back into from its own effect handler, an effect handler that threw, and a module instance an exception escaped from.

    Argument errors the C ABI can't represent — a column count that doesn't fit its uint16_t, a fractional size — are RangeErrors thrown before any call.

  • fuz_terminal/ghostty_key_encoder.ts

    Key events to the bytes a program expects: libghostty-vt's key encoder, following its terminal's modes.

    A GhosttyKeyEncoder belongs to one terminal. It takes a plain description of a key event (GhosttyKeyInput) — no DOM — copies the terminal's input modes into the library's encoder before every encode (cursor and keypad application modes, backarrow mode, the alt escape prefix, modifyOtherKeys, and the Kitty keyboard protocol's flags), and returns the bytes for the PTY, which may be none. So a mode a program changed in output written just before a key press decides what the key sends.

  • fuz_terminal/ghostty_manifest.ts

    libghostty-vt's type manifest: the JSON ghostty_type_json() returns, describing every public C type of the build it came from — enum values, struct sizes and field offsets, packed bit positions, and the value type behind each option key.

    The binding reads every constant and offset it uses from here rather than hardcoding them, as upstream asks: the layouts are only promised for the build that reports them. Each lookup validates the entry it returns and throws a GhosttyManifestError naming it when it's missing or reshaped, so a bad entry fails where it's resolved — never as an undefined passed to a wasm call.

  • fuz_terminal/ghostty_memory.ts

    Access to libghostty-vt's wasm linear memory.

    Any export that allocates can grow the memory, which detaches every ArrayBuffer view made before it. GhosttyMemory.bytes and GhosttyMemory.view are the one place that knows about growth: they return views of the live memory, cached until its buffer is replaced or resized, so they're cheap to call per access. Callers use a view before their next export call and never hold one across it. Pointers stay valid across growth; they are numbers normalized to unsigned, since a wasm i32 result above 2 GiB arrives negative.

    Scratch allocations go through GhosttyMemory.with_scratch and GhosttyMemory.with_opaque, which free what they allocated, with the length it was allocated with, on every path. Buffers the library allocates itself (a formatter's output) are freed with ghostty_free by their callers instead, per upstream's rule never to mix the families.

  • fuz_terminal/ghostty_paste.ts

    Pasting text into a terminal: libghostty-vt's paste encoder and its safety rule, under the terminal's bracketed paste mode (2004).

    GhosttyTerminal.encode_paste is the entry: it reads the mode, applies get_ghostty_paste_hazard, and encodes with ghostty_paste_encode, which replaces the control bytes xterm strips from a paste (NUL, BS, ENQ, EOT, ESC, DEL, and the tty's special characters: Ctrl+C, Ctrl+\, Ctrl+U, Ctrl+Z, Ctrl+Q, Ctrl+S, Ctrl+W, Ctrl+V, Ctrl+R, Ctrl+O) with spaces, then frames the text in ESC [200~ … ESC [201~ when the mode is on, or turns each newline into a carriage return when it's off. Every change is an ASCII byte for an ASCII byte, so the encoded length is known before encoding (to_ghostty_paste_length). Nothing is sent: the caller sends the bytes, as it does a key's.

    The library's own ghostty_terminal_paste makes the same bytes — with no clipboard read effect registered (the binding registers none), a Kitty paste event (mode 5522) never happens — but it reads its text through a callback and streams the result through write_pty; encoding here hands the caller the whole result, to measure before anything is sent.

  • fuz_terminal/ghostty_render_frame.ts

    The plain, immutable data a frame reader produces and a renderer draws from: the update's dirtiness, rows of styled runs placed on their columns, the cursor, and the colors.

    None of it references wasm memory, and none of it is mutated: a value that changes is replaced, so comparing references tells a renderer what to redraw. GhosttyRenderState (ghostty_render_state.ts) reads it from the library; the renderer's pure helpers take it without that dependency.

  • fuz_terminal/ghostty_render_state.ts

    The render-state reader: a terminal's screen as plain frame data a renderer draws — the rows in order, each a list of styled runs of text placed on their columns, the cursor, and the colors.

    A GhosttyRenderState is libghostty-vt's render state — a copy of what one frame needs, updated in place and tracking what changed — read into JS values once per update. The renderer calls GhosttyRenderState.update once per animation frame, draws what changed, and calls GhosttyRenderState.clean. Everything it reads is plain data with no reference into wasm memory, and is never mutated: a value that changes is replaced, so comparing references tells a renderer what to redraw.

    No DOM here: turning a run's style into CSS, boxing wide characters, and drawing the cursor are the renderer's.

  • fuz_terminal/ghostty_terminal.ts

    A libghostty-vt terminal: the emulator's screen, scrollback, and modes, fed program output as bytes and read back as text, and telling its host what the output asks for through the effects it registers.

    Nothing here draws or takes input (GhosttyKeyEncoder turns keys into bytes for the PTY, and GhosttyTerminal.encode_paste a paste). A query in the output (cursor position, device attributes) is answered only through a registered write_pty effect — with none, it gets no reply. No clipboard effect exists.

  • fuz_terminal/ghostty_vt.ts

    The libghostty-vt wasm module, loaded: Ghostty's terminal emulator compiled to WebAssembly, under a binding that runs in Node and browsers alike — no DOM, no Svelte.

    load_ghostty_vt takes the module's bytes (or a fetch Response, or a compiled module) from its caller; this library never fetches an app path itself. The result, a GhosttyVt, holds the instance, its type manifest, its memory, and its build info; handles such as GhosttyTerminal are made from it.

  • fuz_terminal/wasm_trampoline.ts

    Wasm functions made from JS functions, for a wasm module's function table.

    A C function pointer in a wasm module is an index into its __indirect_function_table, and a table slot holds only a wasm function — a plain JS function can't go in. create_wasm_trampoline makes one that can: it assembles a tiny module that imports the JS function under a given signature and exports it again, and the export is a wasm function wrapping the import. This works in every engine, with no reliance on the WebAssembly.Function constructor.

    The module is compiled synchronously. That's fine on a browser's main thread: engines refuse a synchronous compile there only for a module over a size limit of kilobytes, and a trampoline is tens of bytes. A page whose Content-Security-Policy doesn't allow wasm compilation ('wasm-unsafe-eval') can't compile it — nor, under the same policy, the module it serves.
