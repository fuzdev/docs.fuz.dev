FuzTerminalOptions

fuz_terminal/fuz_terminal_state.svelte.ts view source

FuzTerminalOptions import type {FuzTerminalOptions} from '@fuzdev/zzz/fuz_terminal/fuz_terminal_state.svelte.js';

A terminal view's host: what it's given once, and the callbacks it calls. FuzTerminal passes its props, which are read lazily — module and scrollback_max_bytes once, when the view starts; each callback whenever it's called, so a callback prop can change.

The callbacks for the terminal's effects (ondata, ontitle, onbell) run synchronously inside the write that fired them; none is called once the view is destroyed. An exception from any callback is caught: it never escapes a frame or a write, and is reported through onerror (or the console) and the view's notice.

module

The compiled libghostty-vt module, or a promise of it (a fetch and compile in flight: the view is loading until it settles, and failed if it rejects). The view instantiates its own instance of it.

type Module | Promise<Module>

scrollback_max_bytes?

The most scrollback to keep, in bytes; defaults to the library's small limit.

type number

accepts_input?

Whether the view takes keys; defaults to true. Off — say, the program has exited — a key is neither encoded nor prevented, so the browser's default runs (Tab moves focus); the view still draws, selects, copies (a copy chord included, handle_key), and resizes, and its cursor is drawn as when unfocused.

FuzTerminalPasteOptions
#

fuz_terminal/fuz_terminal_state.svelte.ts view source

FuzTerminalPasteOptions import type {FuzTerminalPasteOptions} from '@fuzdev/zzz/fuz_terminal/fuz_terminal_state.svelte.js';

How FuzTerminalState.paste treats one paste.

allow_unsafe?

The risk the person pasting confirmed — a rejected result's hazard and mode: text with that hazard in that mode is sent rather than refused. Unsafe text whose hazard or mode differs now (the program toggled bracketed paste since the person was asked) is rejected again. Defaults to null: unsafe text is rejected (GhosttyPasteOptions.allow_unsafe).

type GhosttyPasteRisk | null

max_length?

The most the paste may send, in UTF-16 code units of its bytes decoded as UTF-8 — the encoded text, framing included (to_ghostty_paste_length). Over it, nothing is sent, and the result is too_large before the text's safety is looked at, so a paste that can't fit is never asked about. Defaults to no limit.

type number

FuzTerminalPasteResult

FuzTerminalPasteResult

type { readonly kind: "pasted"; readonly length: number; } | { readonly kind: "empty"; } | ({ readonly kind: "rejected"; } & GhosttyPasteRisk) | { readonly kind: "too_large"; readonly length: number; } | { readonly kind: "unavailable"; readonly reason: "not_ready" | "input_off" | "busy"; }

import type {FuzTerminalPasteResult} from '@fuzdev/zzz/fuz_terminal/fuz_terminal_state.svelte.js';

What FuzTerminalState.paste did:

  • pasted - the bytes went to ondata; length is the encoded text's, measured as FuzTerminalPasteOptions.max_length is
  • empty - there was no text, so nothing was sent
  • rejected - the text could inject commands (get_ghostty_paste_hazard) and fits max_length, so nothing was sent; ask the person about the hazard, then paste again with allow_unsafe set to the hazard and mode reported here
  • too_large - the encoded text's length is over max_length, so nothing was sent, whether or not the text is safe
  • unavailable - the view isn't taking input: not ready (not_ready: loading, failed, poisoned, or destroyed), its input off (input_off: FuzTerminalOptions.accepts_input), or called from one of its callbacks inside a write (busy), where the bytes would land among its replies

FuzTerminalState

fuz_terminal/fuz_terminal_state.svelte.ts view source

import {FuzTerminalState} from '@fuzdev/zzz/fuz_terminal/fuz_terminal_state.svelte.js';

One terminal view's emulator and frame data. Not a Cell: it holds a wasm instance and DOM elements, and serializes nothing.

Owned by FuzTerminal, which calls attach once mounted (loading starts there, never on the server) and destroy on unmount, which frees the terminal and its reader and drops the instance, so its memory can be collected.

Each frame — at most one per animation frame, and only after output, a resize, or a render hold ending — updates the reader and takes what changed: rows when the update wasn't clean, and cursor and the colors by reference every frame, since they change on clean updates too.

handle_key

A key event on the focused view: a keydown's press or repeat, or a keyup's release, encoded under the terminal's modes as they are now, and its bytes, if any, sent to ondata.

Not taken — nothing encoded or sent — while the view isn't ready or its input is off (FuzTerminalOptions.accepts_input; a key held as input turned off sends no release), for a keydown in a composition (an IME's, or a dead key's: the composed character arrives as a later keydown) or one the browser and the OS keep (should_fuz_terminal_pass_key), and for a keyup whose keydown wasn't taken. A taken keydown's keyup is always encoded, whatever its modifiers are by then. A release sends bytes only under the Kitty keyboard protocol with event reporting on; the encoder decides. The keys follow FuzTerminalDeps.key_platform's conventions.

A copy chord's keydown (is_fuz_terminal_copy_key: Ctrl+Alt+C, Ctrl+Insert) while the selection takes some of the view's text (FuzTerminalDeps.read_selection) copies it instead (FuzTerminalDeps.write_clipboard): nothing is encoded or sent, and the key isn't held, so its release sends nothing either. That's the case whatever the status or accepts_input, since a stopped view still shows its last frame. A failed write is reported, never thrown. With no selection there, the chord is a key like any other.

whether the key was handled — bytes sent, or a selection copied: the caller prevents the event's default exactly then, so a modifier alone, or a key the encoder has nothing for, keeps its default

paste

Paste text: encoded under the terminal's modes as they are now (GhosttyTerminal.encode_paste — bracketed when the program asked for bracketed paste, control bytes replaced) and sent to ondata in one call, as a key's bytes are. Nothing is sent unless the view takes input — ready, its input on, and not inside a write — nor for text that could inject commands unless allow_unsafe names its hazard in the current mode, nor past max_length — checked first: a paste goes whole or not at all, and one too large is never reported as rejected.

A failure of the library stops the view, as for a key; the result is then unavailable.

FuzTerminalStatus
#

fuz_terminal/fuz_terminal_state.svelte.ts view source

FuzTerminalStatus

type { readonly kind: "loading"; } | { readonly kind: "ready"; } | { readonly kind: "failed"; readonly error: unknown; readonly message: string; } | { readonly kind: "poisoned"; readonly error: unknown; readonly message: string; }

import type {FuzTerminalStatus} from '@fuzdev/zzz/fuz_terminal/fuz_terminal_state.svelte.js';

Where a terminal view is:

  • loading - waiting for its module, instantiating it, creating its terminal
  • ready - drawing
  • failed - the module didn't arrive, compile, or instantiate, the terminal couldn't be created, or the library failed; nothing more is drawn or written
  • poisoned - an exception escaped a call into the module instance (GhosttyVt.poisoned); nothing more is drawn or written, and the host recovers by mounting a new view

FuzTerminalWriteOptions

FuzTerminalWriteOptions import type {FuzTerminalWriteOptions} from '@fuzdev/zzz/fuz_terminal/fuz_terminal_state.svelte.js';

How FuzTerminalState.write treats one write.

replay?

Output written earlier, replayed (a buffered history): it's processed with no reply effects registered, so a query in it gets no reply and a bell in it rings nothing — whenever it arrives and whatever it's interleaved with. A title it sets still reaches ontitle, and a render hold it starts is honored. What it does to the terminal's state carries forward, as when live output continues it: a query it ends partway through is answered once live output completes it.

type boolean
