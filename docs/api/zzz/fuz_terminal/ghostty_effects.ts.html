fuz_terminal/ghostty_effects.ts

Effects: the callbacks through which a libghostty-vt terminal asks its host for what it can't do itself — reply to the program (write_pty), ring the bell, announce a new title or working directory, hold the screen still while the program redraws it (render_hold).

GhosttyTerminal.set_effect registers and clears them; this module holds what they share. Each effect has one trampoline per module instance, a slot in its function table (GhosttyCallbackTable) added the first time any terminal registers that effect. The library passes every callback the terminal handle it fired for, and GhosttyEffectRouter dispatches on it to the terminal attached under that handle — so the table grows by at most one slot per effect however many terminals come and go. No userdata pointer is set.

An effect left unregistered is ignored by the library: a query gets no answer, a bell rings nowhere. That's how output is replayed without answering stale queries — feed it with no write_pty registered. The other effects the library has (clipboard read and write, desktop notifications, the size, color-scheme, device-attributes, enquiry, and XTVERSION responders, semantic prompts, unknown sequences, and more) aren't bound, so they're never registered. The clipboard ones stay that way until there's a way to ask the person first.

GhosttyTerminalEffectHandlers

GhosttyTerminalEffectHandlers import type {GhosttyTerminalEffectHandlers} from '@fuzdev/zzz/fuz_terminal/ghostty_effects.js';

The handler for each effect a terminal can register. Each runs synchronously, in the middle of the GhosttyTerminal.write (or resize) that fired it, so it must be quick. It may read the terminal (GhosttyTerminal.format_text), but writing, resizing, disposing, or changing effects on the same terminal throws GhosttyReentrancyError. An exception it throws is caught, and surfaces from the method that fired it once that call has finished. Its return value is ignored — a promise included, so an async handler must catch its own errors, or its rejection goes unhandled.

render_hold

A render hold began (held is true: the program set synchronized output, mode 2026, to redraw without being seen halfway) or ended (false: the program reset the mode, the terminal was fully reset, or it was resized). The library reports only real changes — setting the mode during a hold, or resetting it without one, fires nothing — so true and false alternate. A handler registered during a hold sees its end without its beginning, and a terminal disposed during one never reports its end: a renderer tracks the hold itself and drops it with the terminal. When a hold begins the terminal holds exactly the frame the program wants left on screen — nothing after the mode set has been parsed yet, even later bytes of the same write — so a renderer updates its GhosttyRenderState here, then leaves it alone until the hold ends. The terminal has no clock and never ends a hold itself: a renderer that sees one last too long (a second is usual) stops honoring it and updates again.
