fuz_terminal/ghostty_key_encoder.ts

Key events to the bytes a program expects: libghostty-vt's key encoder, following its terminal's modes.

A GhosttyKeyEncoder belongs to one terminal. It takes a plain description of a key event (GhosttyKeyInput) — no DOM — copies the terminal's input modes into the library's encoder before every encode (cursor and keypad application modes, backarrow mode, the alt escape prefix, modifyOtherKeys, and the Kitty keyboard protocol's flags), and returns the bytes for the PTY, which may be none. So a mode a program changed in output written just before a key press decides what the key sends.

GhosttyKeyEncoder
#

fuz_terminal/ghostty_key_encoder.ts view source

import {GhosttyKeyEncoder} from '@fuzdev/zzz/fuz_terminal/ghostty_key_encoder.js';

libghostty-vt's key encoder for one terminal, with one reusable key event and its own buffers: after the first few keys, encoding allocates nothing in the module.

Made over a terminal, it's freed by GhosttyKeyEncoder.dispose or with its terminal, which disposes it first. Any use afterward throws GhosttyDisposedError; on a poisoned instance (GhosttyVt.poisoned) encode throws GhosttyPoisonedError before calling in, and dispose frees nothing.

A terminal may have any number of encoders — encoding reads the terminal's modes and changes nothing in it — and encode may be called from the terminal's effect handlers.

to_classic_ctrl_chord_bytes
#

fuz_terminal/ghostty_key_encoder.ts view source

(input: GhosttyKeyInput, encoded: Uint8Array<ArrayBufferLike>): Uint8Array<ArrayBufferLike> | null import {to_classic_ctrl_chord_bytes} from '@fuzdev/zzz/fuz_terminal/ghostty_key_encoder.js';

The classic C0 bytes for Ctrl+[, Ctrl+I, Ctrl+M, and Ctrl+@ — ESC, Tab, CR, and NUL — in place of the fixterms CSI … u form libghostty-vt encodes them as in legacy mode, or null to keep the library's bytes.

This departs from the library on purpose. It keeps those four distinct from Escape, Tab, Enter, and Ctrl+2 even when no keyboard protocol is on, but a program that has asked for nothing — bash's readline (whose vi mode takes Ctrl+[ for Escape), less, nano, a plain REPL — doesn't parse CSI u, and sees junk. So the rewrite applies only to the library's legacy fixterms output: the caller checks the Kitty keyboard flags are off, and under xterm's modifyOtherKeys mode 2, which the C API doesn't expose, the library's output is CSI 27 ; … ~, never this form, so it's kept as the program asked. Modified Enter, Tab, and Escape keep the library's sequences in every mode.

The chord is found as the library finds the character for its other C0 chords: the text when it's one byte, otherwise — with Ctrl alone — the physical key's US character (so German Ctrl+Ü, on the US [ key, is ESC, as Ctrl+C is ^C on a Russian layout); a capital from CapsLock is lowered by the unshifted code point. The chord is Ctrl alone or with Alt (Shift too for @, which needs it on a US layout); Ctrl+Shift+I and Ctrl+Shift+M stay distinct. With Alt (not used up making the text) it's ESC-prefixed, as the library prefixes its other Ctrl+Alt chords.
