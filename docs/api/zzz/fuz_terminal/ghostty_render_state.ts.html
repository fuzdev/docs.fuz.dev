fuz_terminal/ghostty_render_state.ts

The render-state reader: a terminal's screen as plain frame data a renderer draws — the rows in order, each a list of styled runs of text placed on their columns, the cursor, and the colors.

A GhosttyRenderState is libghostty-vt's render state — a copy of what one frame needs, updated in place and tracking what changed — read into JS values once per update. The renderer calls GhosttyRenderState.update once per animation frame, draws what changed, and calls GhosttyRenderState.clean. Everything it reads is plain data with no reference into wasm memory, and is never mutated: a value that changes is replaced, so comparing references tells a renderer what to redraw.

No DOM here: turning a run's style into CSS, boxing wide characters, and drawing the cursor are the renderer's.

GhosttyRenderState
#

fuz_terminal/ghostty_render_state.ts view source

import {GhosttyRenderState} from '@fuzdev/zzz/fuz_terminal/ghostty_render_state.js';

A terminal's render state and the reader over it: the frame data a renderer draws, updated once per animation frame.

const frame = new GhosttyRenderState(terminal); // each animation frame if (frame.update() !== 'clean') draw_rows(frame.rows); draw_cursor(frame.cursor, frame.colors); frame.clean();

GhosttyRenderState.update copies everything out of wasm memory, so what it gives is plain data that stays valid through later writes, until the next update replaces it. Every value is immutable and replaced only when it changes: rows is a new array after every update that isn't clean, but each row in it is the previous update's object when the row is unchanged; cursor, colors, and colors.palette are new objects only when they changed. So a renderer compares references to skip work — a keyed list of rows by GhosttyRenderRow.id re-renders only rows whose object changed.

It's freed by GhosttyRenderState.dispose, or with its terminal, which disposes it first. Any use afterward throws GhosttyDisposedError; on a poisoned instance (GhosttyVt.poisoned) every method but dispose throws GhosttyPoisonedError before calling in, and dispose frees nothing.

A terminal has at most one live render state: an update consumes the terminal's change tracking, so a second one would miss what the first took. Its output is plain immutable data, so any number of views can share one reader's rows. Once it's disposed, a new one can be made; its first update is a full frame.

All of it may be used from the terminal's effect handlers, which run in the middle of its write or resize: an update reads the terminal and consumes its change tracking but never changes what it shows, and the library fires every effect between whole steps of the parse, so the terminal is consistent there. That's what a render_hold handler does (GhosttyTerminalEffectHandlers.render_hold). Nothing here throws GhosttyReentrancyError.

The library misses one change: with grapheme clustering (mode 2027) off, a combining mark or other zero-width character that arrives in a write of its own joins the cell before it without marking the row changed, so the update is clean and the row keeps showing the cell without it — until anything else changes that row, which brings it back right. With mode 2027 on, or the mark in the same write as its base, it's tracked.

update

Capture the terminal's current frame, and read what changed into rows, cursor, colors, and cols. A clean update costs two calls into the module and allocates nothing (unless the cursor or a color changed). An update only ever adds to what's dirty — the result stays partial or full until GhosttyRenderState.clean.
