fuz_terminal/ghostty_terminal.ts

A libghostty-vt terminal: the emulator's screen, scrollback, and modes, fed program output as bytes and read back as text, and telling its host what the output asks for through the effects it registers.

Nothing here draws or takes input (GhosttyKeyEncoder turns keys into bytes for the PTY, and GhosttyTerminal.encode_paste a paste). A query in the output (cursor position, device attributes) is answered only through a registered write_pty effect — with none, it gets no reply. No clipboard effect exists.

GHOSTTY_TERMINAL_MAX_SIZE
#

fuz_terminal/ghostty_terminal.ts view source

2048 import {GHOSTTY_TERMINAL_MAX_SIZE} from '@fuzdev/zzz/fuz_terminal/ghostty_terminal.js';

The largest width or height, in cells, a terminal may have. The C API takes any uint16_t, but the screen is allocated up front and wasm memory never shrinks: at 16000 × 16000 a terminal takes about 3 GB, and a failed create or resize near the uint16_t limit leaves about 4 GB grown for good. At this cap, a full screen of styled text — created, formatted, resized — takes tens of MB, and it's still far wider and taller than any real viewport, so a bad cell measurement is refused rather than obeyed.

GhosttyTerminal
#

fuz_terminal/ghostty_terminal.ts view source

import {GhosttyTerminal} from '@fuzdev/zzz/fuz_terminal/ghostty_terminal.js';

A terminal emulator instance in a GhosttyVt module's memory.

Its handle and the formatter it reads text through are freed by GhosttyTerminal.dispose, which nothing does for you: call it when the terminal is done with. Any use after that throws GhosttyDisposedError.

Handles made over it — a GhosttyRenderState, a GhosttyKeyEncoder — are disposed with it, first.

Effect handlers (GhosttyTerminal.set_effect) run inside write and resize, while the library is mid-parse. From a handler the terminal can be read (format_text, disposed, a GhosttyRenderState of it updated), but write, resize, dispose, and set_effect throw GhosttyReentrancyError: the library isn't reentrant and doesn't check. A handler's exception is caught inside the callback, the call finishes, and the call then throws a GhosttyEffectError with the first exception as its cause. An exception that escapes the library anyway (a trap, the JS stack running out) poisons the instance (GhosttyVt.poisoned): every method then throws GhosttyPoisonedError, and dispose frees nothing.

dispose

Free the terminal, the formatter it reads through, and its write buffer — its dependents first: each GhosttyRenderState and GhosttyKeyEncoder made over it is disposed before anything of the terminal's is freed. Idempotent; any other use afterward throws GhosttyDisposedError.

The terminal is detached from effect dispatch before anything is freed. Its library-side effect registrations aren't cleared one by one: they live in the terminal, which ghostty_terminal_free releases whole, and nothing can fire them once the handle is gone.

On a poisoned instance (GhosttyVt.poisoned) nothing is freed — no call goes into the module — and the handles are just dropped: the memory goes with the instance. That never throws.

type (): void

returns void

throws

  • GhosttyReentrancyError - from an effect handler: the terminal is mid-write, and freeing it would pull it out from under the parser

disposed
