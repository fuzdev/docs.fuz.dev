Gates

  • Release audit (every change): A forbidden crate or a test-only feature in a release build, a broken layering rule, and a copied lint table that has drifted. Where: fuz, fuz_forge and zap. pglet runs an audit of its own, for its test-only crate alone.
  • Required programs and suites (every change): A suite that passes by skipping: a program a test needs is missing, or a database suite is left off the CI list. Where: zap for programs, fuz for the CI list.
  • Mutation gate (ci): A test that passes whether or not the code is right. Where: fuz's install script.

Values

The order fuz states its priorities in, highest first (fuz's values):

  1. security
  2. performance
  • Cited for how claims are made: fuz's policy to say planned when a thing is not built
  • What a reader can verify, content addressing: fuz names a built artifact by the hash of its binaries
  • What a reader can verify, content addressing: fuz re-hashes the binaries before every switch to an artifact, and fuz artifact verify runs the same check on request
  • What a reader can verify, signing: fuz checks a release's Ed25519 signature against keys built into the binary, and the installing side links verification only, never the code that signs
  • What a reader can verify, signing: fuz's verification flow checks the manifest's signature before any release bytes are fetched, then the hash of the tarball and of each binary, and stops at the first failure
  • A limit of what a reader can verify, signing: fuz's docs list the hosted install channel as not yet there: nothing is published to fetch
  • A limit of what a reader can verify, signing: On a binary install the built-in key is the root: trusting the first binary means trusting every later release that key signs
  • What a reader can verify, reproducible builds: fuz has fuz artifact build --verify, which rebuilds and compares the output hashes
  • A limit of what a reader can verify, reproducible builds: fuz lists reproducible builds with attestations from outside rebuilders as deferred
  • What a reader can verify, release log: fuz's release log check reads one signed, append-only list of releases from every configured witness, and requires the release to be a row of it with the same hashes, not revoked
  • What a reader can verify, release log: Publishing with a log repository named records the release in that list
  • A limit of what a reader can verify, release log: The check is implemented and inactive by default: no public release log exists, and nothing happens unless the address of one is set
  • A limit of what a reader can verify, release log: Its limits: a bad release becomes public and permanent and is not prevented, and a witness serving an old list hides a newer withdrawal
