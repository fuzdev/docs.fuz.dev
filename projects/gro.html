# the prefix must be there, so a scan that read nothing fails

          excused = 1
          break

    }

Gates

  • Types, tests, lints and format (every change): Type errors, regressions, lint errors and style drift. Where: The repos whose check script runs gro's check, with lints where the repo has a lint config. pglet's check script reaches it through a script of its own, for its TypeScript.
  • Drift in generated files (every change): A generated file that no longer matches its source. Where: The repos whose check script runs gro's check, and pglet's TypeScript the same way.
  • A budget for the startup snapshot (every change): A startup snapshot that has grown past its committed budget. Where: gro.
  • Drift in the package exports map (ci): An exports map that no longer matches the source, which the local gate rewrites instead of failing on. Where: The repos with an exports map whose CI runs gro's check with its workspace flag.
  • Build (ci): A broken build. Where: The repos whose CI runs gro's check with its build flag.
  • A clean tree after the run, and no TODO docs at the root (ci): Uncommitted output and a TODO Markdown file at the repo root. Where: The repos whose CI runs gro's check with its workspace flag.
  • Wall time and instruction counts against a base (on demand): A performance regression: tsv fails a row past a committed percentage, and gro asks for a written reason. Where: gro and tsv.
  • zap's CI has no build of gro's runtime, so the tests that evaluate config through it are skipped there, by an explicit allowance

Actions kept with a person

  • Push a tag, which starts a release in CI for tsv and gro (tool refuses, permission rule, dry run by default): The push tool never sends a tag, and raw pushes are denied. The release script of tsv pushes its own tag, and changes nothing without an explicit flag.
  • Publish a package (permission rule, dry run by default, written rule): The harness denies the publish commands, in settings that are not public. The release scripts of tsv, pglet and blake3 change nothing without an explicit flag, which a session could pass. The publish task of gro and the release task of fuz_forge have no such default.
  • Deploy a site or a server (permission rule, dry run by default, written rule): The harness denies the site deploy command, in settings that are not public, and the deploy task of gro has no dry default. A server deploy through zap changes nothing without an explicit flag and runs only a plan it has already previewed, which a session can do itself, so there the written rule is what holds.

Values

The order gro states its priorities in, highest first (gro's runtime design):

  1. security
  2. web standards
  3. developer control and ergonomics
  4. speed, startup first
  5. binary size, memory

Over every choice: simple and small.

  • A decision: speed over security. One realm, mutable intrinsics and the JIT on by default. Cost: Some hardening, which an opt-in tier listed as future work would give back. runtime design
  • Passes the question of security: gro's authority model, where the network is an import and no global carries authority
  • Passes the question of controllability: At the boundary: gro's host modules, where a root imports authority, narrows it and hands it down
  • Passes the question of simplicity: gro's design, where staying simple and small is what keeps the surface small enough to audit
  • Where the stack falls short of security: gro's runtime says its security is not finished, and fuz_forge says its security is not ready to be trusted.
  • Where the stack falls short of controllability: That library code takes its effects as parameters is a written rule, tested only over a named list of gro's own modules, and gro's policy file, the reviewable record of what a project may reach, is designed and not built.
  • A context: A short command, called in a loop. Short-lived runs dominate a loop an agent drives, so the start counts before the steady state. gro's runtime design
  • Cited for how claims are made: gro's design, where the wins are startup, loading, caching and work avoided
  • What a reader can verify, reproducible builds: gro's snapshot build of fgro is reproducible from any path, given the same toolchain and cargo home
  • What a reader can verify, reproducible builds: The comparison that holds gro's build in CI is a row of the oracle table
