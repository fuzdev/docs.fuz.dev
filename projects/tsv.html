Gates

  • Pinned pass counts (every change): Conformance coverage that quietly shrinks or shifts. Where: pglet, and tsv's fixture validation.
  • Links and anchors in Markdown (every change): A dead relative link or anchor in any Markdown file of the repo. Where: tsv.
  • Size limits in CI (ci): A WebAssembly build or a native addon that has grown. Where: tsv and fuz_schema.
  • Conformance against committed ledgers (release): A parser or formatter difference that no ledger records. Where: tsv.
  • Wall time and instruction counts against a base (on demand): A performance regression: tsv fails a row past a committed percentage, and gro asks for a written reason. Where: gro and tsv.
  • tsv's CI skips the two legs of its gate that read sibling checkouts, the wider Prettier round trip and corpus discovery

From Gates. A gate is listed here when its row names the project or links its repo, so one that every repo of a kind runs may be missing.

Actions kept with a person

  • Push a tag, which starts a release in CI for tsv and gro (tool refuses, permission rule, dry run by default): The push tool never sends a tag, and raw pushes are denied. The release script of tsv pushes its own tag, and changes nothing without an explicit flag.
  • Publish a package (permission rule, dry run by default, written rule): The harness denies the publish commands, in settings that are not public. The release scripts of tsv, pglet and blake3 change nothing without an explicit flag, which a session could pass. The publish task of gro and the release task of fuz_forge have no such default.
  • Create a package or a crate (written rule): Only a written rule: the release audit checks the crate graph, not new members, and tsv asks only that a new crate declare whether it publishes.

Values

The order tsv states its priorities in, highest first (The tsv README):

  1. correctness
  2. speed
  3. binary size, memory usage
  4. extensibility, modularity, reusability

Over every choice: staying simple.

  • A decision: speed over size. Profile-guided builds for the shipped CLI and native addon. Cost: Larger binaries. performance
  • A decision: speed over simplicity. A cleanup of a hot path is measured like any change, and refused when it costs time. Cost: Code that stays less tidy than it could be. performance
  • A context: A tool that runs for a while. The usual order: speed first, then the binary and its memory. The tsv README
