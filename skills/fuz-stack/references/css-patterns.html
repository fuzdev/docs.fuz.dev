CSS Patterns

fuz_css is three parts: semantic styles (classless element defaults), style variables (design tokens as CSS custom properties), and optional utility classes generated per-project with only the classes you use.

Default styling is the baseline

The single most common mistake is styling elements fuz_css already styles. Headings are tiered, form controls share sizing and states, <code>/<pre> are mono, <aside> is a callout, and block elements space themselves: p, ul, ol, menu, form, fieldset, table, details, textarea, select, label, pre, blockquote, aside, nav, legend each get margin-bottom: var(--flow_margin, var(--space_lg)) unless :last-child or .unstyled (section takes a larger multiple of it). A stack of paragraphs, a heading over prose, a list under a heading — correct rhythm with zero classes.

Before adding any class or <style>, ask: what specific gap in the defaults does this close? Hand-adding mb_*/gap_*/p_* where flow margin already spaces, or re-declaring the color/font an element carries, fights the framework. Most fuz app source files have no <style> block, and where classes appear it's one or two, not long strings.

Reach past the defaults for genuine layout (flex rows/columns, grids), intent color (palette_c for a destructive button), or component-specific behavior. Flex containers are the main reason to add classes at all — inside a .row or .row_wrap, child flow margins reset to 0 (.row > *, .row_wrap > * → margin: 0), so use gap_* there.

The Styling Ladder

Stop at the first rung that suffices:

  1. Semantic HTML — the right element, no class. Often the whole job.
  2. Built-in class conventions — .selected, .disabled, .palette_a–.palette_j, .inline, .unstyled — state/variant classes the semantic styles already recognize.
  3. Composite classes — box, row, row_wrap, column, panel, chip, ellipsis.
  4. Token and keyword classes — p_md, gap_lg, color_a_50; never hardcode spacing or color. Keyword classes are bare CSS keywords that name their property (flex, sticky, uppercase), plus hidden (display: none).
  5. Literal classes — justify-content:space-between, width:100%, hover:opacity:80%.
  6. <style> block with design tokens — component-specific layout, animation, complex selectors, theming APIs.

Rungs 3–5 are one tier, mixed freely on the same element: a composite when one exactly matches (row over flex align-items:center), tokens for spacing/color, keywords and literals for one-off layout. Spacing tokens are the most-used family and flex classes (flex, flex:1, width:100%) are as common as composites. The real cut points are rung 1 vs the rest, and rungs 1–5 vs rung 6. Mixing has one rule: a token, keyword, or literal class beats a multi-property composite on the same property, modified or not, since composites render in a lower sublayer. Same for text: <small> over font-size: var(--font_size_sm), <aside> over a hand-built callout. Never hand-write a rem font size: fuz_css sets a 62.5% root, so 0.85rem renders ~8.5px — smaller than the --font_size_sm text around it. Every other rem length in a rule or a container query scales the same way (16rem is 160px), but a @media query's rem is the browser's initial 16px, which is why the breakpoint modifiers below read 40rem for 640px. Prefer tokens; when a hand-written length is unavoidable, pick its unit knowing which of the two it gets.

Direction matters — don't churn <style> into class soup

The ladder describes how to author, not a mandate to rewrite <style> blocks. Pushing styling up (<div class="callout"> → <aside>) is good; pushing it down (a working <style> → a 12-class string) is churn.

  • Trivially-redundant <style> → composite/token — only when the block's entire content is one composite's worth (display: flex; flex-direction: column; gap: var(--space_md) → column gap_md) and intent survives verbatim.
  • Non-trivial <style> → class string — don't. Hover/focus state machines, animations, @media, parent-child selectors, pseudo-element content, positioning, theming variables all stay in <style>, which also gets IDE autocomplete and composes with conditional logic without clsx gymnastics.

When in doubt, leave an existing <style> block alone.

Project Setup

Import Order

In src/routes/+layout.svelte:

import 'virtual:fuz.css'; // generated bundled CSS (all projects) import '@fuzdev/fuz_code/theme.css'; // package-specific themes (if any) import './style.css'; // project-specific global styles (app projects)

Library repos (fuz_css, fuz_ui, gro) omit the project style.css; app repos use all three.

CSS Generation

The vite_plugin_fuz_css Vite plugin generates CSS on demand as the virtual:fuz.css module — no committed fuz.css:

// vite.config.ts import { vite_plugin_fuz_css } from '@fuzdev/fuz_css/vite_plugin_fuz_css.ts'; export default defineConfig({ plugins: [vite_plugin_fuz_css()] });

It returns several plugin objects (pass them as is), needs Vite 6+, and goes after any plugin that rewrites CSS in its transform hook.

// src/app.d.ts declare module 'virtual:fuz.css' { const css: string; export default css; }

HMR works. The default tree-shaken bundled mode needs no options; the dev-only prescan option eagerly scans sources so the first served CSS is complete. fuz_css itself passes additional_elements: 'all', additional_variables: 'all', and a computed additional_classes list for its docs demos.

Project style.css

src/routes/style.css holds custom element overrides, patterns being prototyped before upstreaming to fuz_css, and app layout (sidebar widths, nav heights). Keep it near-empty. When a pattern recurs across an app's components but isn't general enough for fuz_css, it belongs here (mark // TODO upstream candidates), not repeated per component.

Style Variables (Design Tokens)

Defined in TypeScript, rendered to CSS; each token has light and/or dark values.

Colors

10 palette hues: a (blue · accent), b (green · positive), c (red · negative), d (purple), e (yellow), f (brown · neutral), g (pink), h (orange · caution), i (cyan · info), j (teal).

Semantic intent knobs alias meaning over the letters — --hue_accent, --hue_positive, --hue_negative, --hue_caution, --hue_info, plus --hue_neutral/--neutral_chroma for surface/text/border tint. Each intent derives a 13-stop scale (--accent_00–--accent_100) with text/background token classes (positive_50, bg_caution_10) and the palette letters' border, outline, and shadow twins (border_positive_50, outline_accent_60, shadow_negative_40) - prefer intent tokens over palette letters when the color carries meaning. Caveats: intent naming covers the token classes only (the button/chip rung stays .palette_a–.palette_j; there is no .negative button class), and the neutral has no neutral_00–neutral_100 family (its scales are shade_*/text_*).

Intensity scale: 13 scheme-adaptive stops 00, 05, 10, 20, 30, 40, 50, 60, 70, 80, 90, 95, 100. Variables run --palette_a_00 (nearest the background) → _50 (base) → _100 (highest contrast); token classes are color_a_00–color_a_100 — property-first, the letter implies the palette.

Color-Scheme Variants

These are variable families. text_* and shade_* are the everyday opaque tokens — reach for them first; ink_*/paper_* overlays use alpha and accumulate when nested. text_*, shade_*, darken_*, lighten_* exist as classes too, but ink_*/paper_* have no token classes (the bg_ class prefix is the opaque backgrounds, bg_a_50, bg_positive_50), so reach the adaptive overlays via literals (background-color:var(--ink_10)). shade_* and text_* have _min/_max for untinted extremes. For a color that doesn't adapt to the scheme, write the literal or define a custom property (the old _light/_dark variants were removed).

Sizes

Spacing: xs5 → … → xs → sm → md → lg → xl → xl2 → … → xl15 (23 stops). Subsets: font sizes 13 (xs–xl9); icon sizes 7 (xs–xl3, px); border radii 7 (xs3–xl); distances 5 (xs–xl, px absolute widths 200/320/800/1200/1600); shadows and line heights 5 (xs–xl).

Additional Variable Families

  • border_color_* — alpha-based tinted borders (00–100). outline_shade_* is a class family over the opaque shade scale (it reads --shade_NN); there is no --outline_shade_NN variable
  • shadow_alpha_* (00–100), border_width_* (1–9 px), duration_* (1–6, 0.08s–3s), hue_* (hue_a–hue_j base hues, OKLCH angles)

Cascade Layers

fuz.base (default variables + element styles) < fuz.preferences (OS preference mappings — prefers-reduced-motion zeroing durations, prefers-contrast: more setting the contrast input the neutral ramps derive from) < fuz.theme (theme overrides, where render_theme_style() renders) < fuz.utilities (generated classes). Consumers' unlayered styles beat everything except two !important declarations: [hidden]'s display: none and the prefers-reduced-motion reset of the duration_* tokens (set a duration on the element that needs one). Colors are derived OKLCH (curve knobs → ramp stops → color stops, computed in pure CSS).

Cascading Variable Pattern

Many token classes set a CSS property and a cascading custom property so children inherit: font_size_lg → font-size + --font_size; icon_size_sm → font-size + --font_size + --icon_size; color_a_50 → color + --text_color; border_color_30 → --border_color; outline_a_50 → --outline_color (focus rings key off it); shadow_color_umbra → --shadow_color.

Token Classes

  • Spacing: p_md, px_lg, mt_xl, gap_sm, gap_0, mx_auto, m_0 — the most-used family
  • Text colors: text_70, text_min, color_a_50
  • Backgrounds: shade_00, darken_30, bg_a_50 (opaque)
  • Typography: font_size_lg, font_family_mono, line_height_md, icon_size_sm
  • Layout: the distance-scale sizers width_atmost_lg/width_atleast_sm/height_atmost_md - emit width: 100%; max-width: var(--distance_*) (px caps 200–1600); space-scale sizes and offsets are literals (width:var(--space_md), top:var(--space_sm))
  • Borders: border_radius_xs, border_radius_0, border_width_2, border_color_30
  • Shadows: shadow_md, shadow_top_md, shadow_inset_xs, shadow_alpha_50, shadow_color_umbra (also _highlight, _glow, _shroud)

Keyword Classes

A CSS value keyword that names its property on its own is a bare class setting that one declaration; a keyword shared across properties (center, nowrap, none) stays a literal (align-items:center).

A class name earns its place by one of: passing that keyword gate, bundling declarations (a composite), being token-backed, or completing a token family's steps (gap_0, border_radius_0). A single non-token declaration never gets a coined name - the literal is the shorthand (flex:1, width:100%, border-radius:50%, white-space:nowrap). hidden is the one named exception: it mirrors the HTML attribute so modifiers can reach it.

  • display: flex, inline-flex, grid, inline-grid, inline-block, block, flow-root
  • position: relative, absolute, fixed, sticky
  • typography: uppercase, lowercase, capitalize, italic, oblique, bold, bolder, lighter, underline, overline, line-through (the decoration ones set the text-decoration-line longhand)
  • rendering: pixelated (image-rendering)
  • hidden: display: none, mirroring the HTML attribute

They order with the token and literal classes and take modifiers like any class (md:flex, hover:underline). flex is plain display: flex; row, column, and box stay the composites that add direction and alignment.

hidden exists for the modifiers the attribute can't take (max-md:hidden, print:hidden); static hiding is the hidden attribute's job, and the attribute beats every class; the class itself loses to a display set in a component <style> block. The class orders after a display:* literal it ties with, so it toggles in a class list, while a media query still outranks it:

<div class={['flex', {hidden: !open}]}> <!-- toggled: hidden wins --> <nav class="max-md:hidden row"> <!-- hidden below md, a row from md up --> <nav class="hidden md:flex"> <!-- hidden until md, then flex -->

Trap: hidden md:row stays hidden at every width — the composite row sits in the lower sublayer, so even modified it loses to hidden. Put the modifier on the single-purpose class: max-md:hidden row.

Keyword classes are found implicitly like any class, so a component-local class named like one (.hidden, .block, .bold) also gets fuz_css's declaration — name local classes in kebab-case that no keyword takes.

Size composites cascade to a subtree. Put one on any container (or a single element, such as a row of secondary buttons) and it rescales that subtree's --font_size, --input_height, --icon_size, padding, and --flow_margin in lockstep — a sized_sm panel gets tighter controls, chips, icons, and rhythm together (headings and prose keep their sizes — each hN re-sets --font_size on itself, body text never reads it). sized_md resets to default inside an already-sized parent. This is how to make a whole region denser or roomier.

Gotcha: composites with rulesets (clickable, selectable, menuitem, plain, chip) already include their state styles — hover:clickable is redundant.

The load-bearing composites are row, column, box, panel, chip, menuitem; pane and chevron see near-zero real use.

Literal Classes

property:value maps directly to CSS. ~ encodes spaces in multi-value properties; calc needs ~ around +/-:

<div class="flex justify-content:center gap:var(--space_md)"> <div class="margin:0~auto padding:var(--space_sm)~var(--space_lg)"> <div class="width:calc(100%~-~20px)">

More than 2–3 ~ → use a <style> block. Custom-property literals (--flow_margin:0, --button_shadow:none, --button_min_height:0 for a button shorter than the input height) are the general escape hatch onto any theme/base variable hook (knobs like --space_scale resolve on :root, so they belong in a theme, not on an element).

Modifiers

Prefixes on any class, each 1:1 with a pseudo-class or at-rule (hover: → :hover, disabled: → :disabled, print: → @media print, before: → ::before); the exhaustive registry is fuz_css's modifiers.ts.

<button class="hover:opacity:80% focus:outline:2px~solid~var(--palette_a_50)"> <div class="hidden md:flex"> <!-- responsive --> <div class="box-shadow:var(--shadow_lg) dark:box-shadow:var(--shadow_sm)"> <div class='before:content:"" before:display:block'> <!-- pseudo needs explicit content -->
  • Breakpoints: sm: (40rem), md: (48rem), lg: (64rem), xl: (80rem), 2xl: (96rem); also max-sm:… and arbitrary min-width(800px): / max-width(600px):
  • Ancestor: dark: / light:
  • Order: [media]:[ancestor]:[state...]:[pseudo-element]:property:value; multiple states must be alphabetical (focus:hover:…), parser-enforced

Modifier classes are rare in real code. Responsive layout is done with @media in <style>, and hover/focus states ride on stateful composites or <style>. The system is correct and available; convention favors <style> beyond an occasional one-off.

Class Extraction

Classes are extracted by AST at build time from class="...", class={[...]} / class={{...}}, class:name directives, clsx() / cn() / cx() / classNames() / classnames() calls, and variables named *class/*classes/*className(s)/*classList(s). CSS variables are additionally caught by a var(--name) regex scan (unknown ones ignored), which catches component props like size="var(--icon_size_xs)".

For dynamically-constructed names, declare them:

// @fuz-classes opacity:50% opacity:75% opacity:100% // @fuz-elements button input textarea // @fuz-variables shade_40 text_50

Auto-detected-but-unresolvable names are silently skipped (they may belong to another framework); an explicit @fuz-* entry that can't resolve is an error with typo suggestions. Outside fuz_css's own docs site, hints are rarely needed.

Dynamic Theming

Runtime variable overrides: components expose CSS variables as their theming API. On elements use style:; on components the custom-property shorthand (style: is invalid on component tags):

<div style:--docs_menu_width={width}> <PendingAnimation --font_size="var(--font_size_xl5)" />

Color scheme is a dark/light class on the root element (style.css has :root.dark { color-scheme: dark; } / :root.light { color-scheme: light; }); persistence and system preference live in fuz_ui's ThemeState / ThemeRoot.

Themes: default_themes registers base and ledger. Contrast is a knob (--contrast, 0–1, the fraction of the way from a theme's ground to its scheme's end): the one modifier, contrast_modifiers.high (a record keyed by the name a picker selects), sets it to 0.5 and composes via compose_themes; the OS prefers-contrast: more preference reaches the same derivation through its own input and only ever raises a theme's contrast, so no theme silences it. There is no low-contrast modifier. Shipped-but-unregistered exemplars under themes/ (zine, pebble, parchment, phosphor, guestbook, marquee, signage — phosphor and marquee dark-only via scheme) show the range. A Theme (from @fuzdev/fuz_css/variable.ts, a strict schema) is a name, an optional summary for pickers, and StyleVariable overrides (variables). A single-scheme scheme stance is resolved with resolve_theme_stance (theme_stance.ts), which returns the theme with its stance mirror beside it (ResolvedTheme), before runtime rendering. render_theme_style() renders it into the fuz.theme layer, which beats fuz.base by layer order regardless of specificity. validate_theme lints its shape and knobs, and check_theme gates gamut, ramp monotonicity, and contrast at the default caps, and compile_theme re-runs them with the theme's recomputed caps; either report (ThemeCheckReport) answers passed (every evaluated gate passes) and complete (nothing left unchecked) separately. The generators also take a build-time theme option, the authored Theme, which derives the mirror and caps itself and bakes the theme into the bundled CSS with no JS; the runtime ThemeRoot path composes on top (runtime wins by layer order).

ThemeRoot (fuz_ui) renders theme_state.theme and persists it. Pass the app's registry as themes (default default_themes): a registry theme saves by name, a registry theme composed with a contrast modifier as {name, contrast} - so a load takes the registry's current version, recomposed - and any other theme whole, trimmed to its authored fields. The matches are by name, so give custom themes names the registry doesn't use. Inject resolve_theme={resolve_theme_stance} when the app ships a stanced theme (phosphor, marquee): without it ThemeRoot throws at creation when themes or theme_fallback holds one, and a stanced theme from elsewhere (storage, set at runtime) logs an error and renders without its mirror. The storage helpers take the registry too - save_theme(theme, themes?, key?), load_theme(themes?, fallback?, key?) - and ThemeRoot calls its save_theme prop with the registry on every theme reassignment, undebounced, so an app that rethemes live (an editor draft) wraps it to skip what it shouldn't persist (app_themes and DRAFT_THEME_NAME are the app's own):

<ThemeRoot themes={app_themes} resolve_theme={resolve_theme_stance} save_theme={(theme, themes) => theme?.name === DRAFT_THEME_NAME ? undefined : save_theme(theme, themes)} > {@render children()} </ThemeRoot>

Components

Minimal custom CSS, delegating to fuz_css. A large share of fuz_ui's components — the styling-heaviest code in the ecosystem — have no <style> block; application code is far more classless still. Where a <style> exists it's short and component-specific: positioning, transitions, breakpoints, parent-child selectors, all values from tokens.

<!-- No <style> needed — semantic HTML + utility classes --> <aside class="column gap_md"> <h2>{title}</h2> <small class="text_50">{subtitle}</small> <p>{description}</p> <button class="palette_a">Confirm</button> <button class={['palette_c', { selected: destructive }]}>Delete</button> </aside>

fuz_ui's Details.svelte and EcosystemLinks.svelte are real zero-<style> examples.

Anti-Patterns

<!-- BAD: rebuilding what <small>/<aside> already do --> <span class="subtitle">{text}</span> <!-- GOOD: <small class="text_70"> --> <div class="info-box">{message}</div> <!-- GOOD: <aside> --> <!-- BAD: manual flex in <style> --> <div class="container">…</div> <!-- GOOD: <div class="column gap_md"> --> <style>.container { display: flex; flex-direction: column; gap: var(--space_md); }</style> <!-- BAD: hand-rolled destructive button --> <button class={['delete-btn', {active}]}>Delete</button> <!-- GOOD: <button class={['palette_c', {selected: pending}]}>Delete</button> --> <!-- BAD: hardcoded pixels --> <style>.sidebar { width: 220px; padding-top: 40px; }</style> <!-- GOOD: <style>.sidebar { width: var(--sidebar_width); padding-top: var(--space_xl2); }</style> -->

When Custom CSS Is Justified

Complex interactive states (.parent:hover .child — fuz_ui's Hashlink.svelte is the canonical reveal); structural behavior (column-reverse for bottom-up scroll, sticky/absolute offsets); @media structural changes; animations and transitions; rendering contexts (canvas, 3D); theming APIs for children (Alert.svelte exposes --text_color). Still tokens, never hardcoded values.

Class Naming

  • fuz_css tokens: snake_case — p_md, color_a_50, gap_lg
  • Component-local classes: kebab-case — site-header, nav-links
<div class="column gap_md site-header"> <nav class="row gap_sm nav-links">…</nav> </div> <style> .site-header { position: sticky; top: 0; z-index: 10; } .nav-links { border-bottom: var(--border_width_1) var(--border_style) var(--border_color); } </style>

kebab-case for local classes is the target, adopted in zzz and fuz_ui; the fuz_css and docs.fuz.dev sites still lean snake_case locally. New code uses kebab-case.
