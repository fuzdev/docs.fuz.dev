The values the Fuz stack is designed against

The purpose is human agency: software one can own, control, extend, and swap out. The values below are what a design is checked against on the way there. The Fuz intro post.

This page is a sketch. It draws the same data several ways, to choose which views are worth keeping. It names only projects on the Fuz stack page. What holds the values in place when agents write the code is on the coherence page.

Claude Fable 5.2 wrote this page and its data file. Its claims were checked against the repos on 2026-11-18. The maintainer has not yet reviewed it.

The values

Each value is stated as a question to ask of a design, with a decision that passes it and where the stack falls short of it. The values are not one kind of thing, which is why no single ranked list holds them:

  • Gate It has to hold before anything else is weighed. correctness security worst case
  • Default The safe form is what happens unless someone asks otherwise. controllability
  • Objective It is pushed as far as it will go. speed startup
  • Budget It is free to spend until a limit is crossed. size memory
  • Overarching It applies to every choice and ranks nowhere. simplicity

Correctness

Ranked as
correctness Gate
Means
The software does what it says and nothing else, held to a reference where one exists.
Asks
What does this accept or produce that it should not?
Passes
  • fuz_schema's priorities, where a fix of over-acceptance goes ahead of speed and size
Falls short
Most projects have no outside reference to be held to, and where one exists the comparison often runs before a release and not on every change.

Security

Ranked as
security Gate
Means
Code acts only on what it was handed, and a misconfiguration with a security consequence fails loudly.
Asks
What can this reach that it was not given?
Passes
  • gro's authority model, where the network is an import and no global carries authority
Falls short
gro's runtime says its security is not finished, and fuz_forge says its security is not ready to be trusted.

Performance

Ranked as
speed Objective startup Objective worst case Gate size Budget memory Budget
Means
Speed is pushed as far as it goes, size and memory are budgets that bind when crossed, and the time or memory an input can force is a limit, not an average.
Asks
Was it measured, on what, and against what?
Passes
  • The fuz-stack performance reference, where a claim comes from a harness and states its noise floor
Falls short
Energy and browser performance are never measured, and memory is gated in one place, the heap fuz_schema's schemas retain.

Controllability

Ranked as
controllability Default
Means
What the software can reach and what it will do are visible, reviewable and bounded before it acts, and doing more is a person's decision.
Asks
Where does a person read what this can do, and who decides when it does more?
Passes
  • In the source: the fuz-stack dependency injection convention, where a side effect is a parameter and a root decides what is passed
  • At the boundary: gro's host modules, where a root imports authority, narrows it and hands it down
  • At run time: zap's rule that a real run executes only a plan it has already previewed
Falls short
That library code takes its effects as parameters is a written rule, tested only over a named list of gro's own modules, and gro's policy file, the reviewable record of what a project may reach, is designed and not built.

Simplicity

Ranked as
simplicity Overarching
Means
Small enough to audit and to hold in one head: few dependencies, few concepts, one way to do a thing.
Asks
What did this design refuse?
Passes
  • gro's design, where staying simple and small is what keeps the surface small enough to audit
Falls short
Twin implementations, hand-written parsers and an owned runtime are complexity the stack chose to take on.

Method

A claim comes from a measurement, the measurement is published where the work loses too, and what was tried and declined is written down with its numbers.

  • The fuz_schema README, which says where it is not the fastest
  • fuz_schema's record of trades that were built, measured and declined
  • fuz's policy to say planned when a thing is not built

By context

Within performance the usual order is speed, then size and memory. The situation changes it, and the documents say why each time.

WhereOrderWhySource
A tool that runs for a while speed > size = memoryThe usual order: speed first, then the binary and its memory.The tsv README
A short command, called in a loop startup > speed > size = memoryShort-lived runs dominate a loop an agent drives, so the start counts before the steady state.gro's runtime design
A library shipped to a browser speed = size > memoryBytes cross a network, so they rank with speed, and a written rule sets what speedup a byte must buy.fuz_schema's grading rules
WASM loaded by a page size > speedThe build is chosen by measurement per runtime, and where bundle size matters the small one is right.The WASM reference
WASM run by a host speed > sizeA host can spend bytes for speed where a browser bundle cannot.The WASM reference
Input a remote party wrote worst case > speed = size > memoryThe time or memory an input can force is ranked with correctness, ahead of speed and size.fuz_schema's priorities
A database for tests size = startup > speedpglet aims to beat PGlite on startup and size, and its throughput only has to stay within a factor of SQLite's.pglet's plan

Efficiency

Performance is the measured result a person feels, ranked by context. Efficiency is the stance under it: every cost names its reason, and the cheapest work is the work not done.

  • fuz_schema's priorities, where a feature not everyone needs is a separate export that bundles to nothing unused
  • gro's design, where the wins are startup, loading, caching and work avoided
